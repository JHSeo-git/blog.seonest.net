# 에이전트는 어떤 개발 사이클을 따르는가

<PostMeta createdAt={metadata.openGraph.publishedTime} />

배포 전 평가에서 90점을 받은 에이전트도 일주일 뒤에는 같은 질문에 다르게 답할 수 있습니다. 그사이 코드를 한 줄도 고치지 않았다면 어디부터 살펴봐야 할까요?

## 에이전트의 답을 바꾸는 것들

기존 소프트웨어 개발 생애주기(SDLC)에서는 코드가 시스템의 동작을 결정한다고 봅니다. 같은 실행 파일에 같은 값을 넣으면 결과도 같다고 보는 겁니다. 원하는 동작을 명세에 적고, 구현한 코드가 테스트를 통과하면 배포하는 절차도 이 전제에 맞춰져 있습니다.

에이전트가 어떻게 답할지는 코드만 보고 알기 어렵습니다. 어떤 모델에 어떤 프롬프트를 주는지, 검색으로 어떤 자료를 가져오는지에 따라 답이 달라집니다. 스킬이나 도구 스키마, 미들웨어를 바꿔도 마찬가지입니다.

우리 쪽에서 아무것도 바꾸지 않았어도 모델 제공자가 가중치를 조정했을 수 있습니다. 검색 인덱스가 갱신돼 전과 다른 문서를 가져오거나 외부 도구가 응답 형식을 바꾸기도 합니다.

LangChain은 이런 변화까지 감안해 에이전트를 개발하고 운영하는 절차를 [Agent Development Lifecycle](https://www.langchain.com/blog/the-agent-development-lifecycle)(ADLC)로 정리했습니다.

## 개발 단계마다 무엇을 챙겨야 할까요?

ADLC에서도 에이전트를 만들고(Build), 평가하고(Test), 배포합니다(Deploy). 배포한 뒤에는 실제 동작을 지켜보고(Monitor) 고칠 곳을 찾아 다시 개발에 들어갑니다(Iterate). 비용과 권한을 관리하는 일(Govern)은 처음부터 끝까지 이어집니다.

- **Build**에서는 코드를 작성하고 프롬프트와 스킬, 도구, 미들웨어를 함께 구성합니다. 도메인 전문가도 프롬프트와 스킬을 직접 편집하며 개발에 참여합니다.
- **Test**에서는 단위 테스트와 통합 테스트에 더해 평가셋으로 에이전트를 시험합니다. 정해 둔 기준으로 답을 채점하고, 여러 차례 대화를 주고받는 상황도 재현합니다. 정답이 하나인 작업에서는 에이전트의 답을 정답과 비교합니다. 여러 답이 가능한 작업은 근거를 제시했는지, 정책을 지켰는지, 불필요한 도구를 호출하지 않았는지 평가합니다.
- **Deploy**에서는 코드와 함께 장시간 작업을 지원하는 실행 환경, 샌드박스, 컨텍스트를 관리하는 허브를 배포합니다. 에이전트가 작업 도중 사람의 결정을 기다려야 할 때도 있으므로 실행 상태를 저장했다가 멈춘 곳에서 이어 갈 수 있어야 합니다. 프롬프트와 컨텍스트는 코드와 별도로 배포합니다.
- **Monitor**에서는 응답 시간과 오류율을 확인하고, 모델과 도구의 호출 기록인 트레이스(trace)도 살펴봅니다. HTTP 200 OK는 요청을 처리했다는 뜻입니다. 사용자가 부탁한 일까지 제대로 해냈는지 알려면 어떤 모델과 도구를 거쳐 답을 냈는지 봐야 합니다.
- **Iterate**는 SDLC의 유지보수와 다릅니다. 운영 중에 수집한 트레이스를 평가셋에 추가하고, 다시 평가해 에이전트를 고치는 일을 반복합니다.

Govern에서는 비용과 도구 접근 권한을 관리하고, 어떤 작업에 사람의 승인이 필요한지 정합니다. 프롬프트와 스킬도 쉽게 찾아 다시 쓸 수 있게 정리합니다. 에이전트 하나라면 간단히 처리할 수 있지만, 조직에서 여럿을 운영하려면 공통 규칙과 관리 절차를 마련해야 합니다.

## 운영 중에 발견한 문제를 다음 평가에 씁니다

어제까지 잘되던 기능이 오늘 갑자기 이상해지면 보통 최근 커밋이나 릴리스 노트부터 살펴보고, 필요하면 `git blame`으로 해당 코드를 누가 언제 고쳤는지 찾습니다. 그런데 모델의 가중치나 외부 도구의 응답이 바뀐 경우에는 우리 저장소를 아무리 뒤져도 그 흔적이 없을 수 있습니다.

신입 사원에게 일을 가르칠 때도 직무기술서 한 장에 모든 판단 기준을 적어 줄 수는 없습니다. 수습 기간에는 과제를 맡겨 보고, 실무에 들어가면 어떤 판단을 거쳐 그런 결과를 냈는지 함께 살펴봅니다. 한 번 실수했다고 내보내기보다는 다음에 어떻게 하면 좋을지 알려 줍니다. 어느 정도 일을 익혔는지 알게 되면 더 어려운 과제도 맡길 수 있습니다. 에이전트에게 과제를 주고 트레이스를 살피는 이유도 비슷합니다.

한 가지 차이가 있습니다. 신입 사원은 어제 한 실수를 기억하지만 에이전트는 같은 일을 다시 맡겨도 지난 경험에서 저절로 배우지 않습니다. 누군가 트레이스에서 그 사례를 골라 평가셋에 넣고, 평가 결과를 보며 프롬프트나 스킬, 컨텍스트를 고쳐야 합니다. 운영 절차에 이 작업이 들어가야 배포 후에도 에이전트를 개선할 수 있습니다.

## 개발을 시작할 때 준비해 둘 일

- **첫 커밋부터 평가셋을 함께 관리합니다.** 출시 직전에 한 번 점검하고 끝내면 다음 버전을 평가할 때도 같은 문제만 풀게 됩니다. 운영하면서 마주친 사례를 트레이스에서 골라 평가셋에 보탭니다.
- **프롬프트와 스킬, 컨텍스트는 코드와 별도로 관리합니다.** 버전 관리와 리뷰, 롤백 절차를 각각 마련합니다. 자주 바뀌는 내용을 매번 코드 릴리스에 맞춰 배포해야 하면 개선이 늦어집니다.
- **사람의 승인이 필요한 작업을 정합니다.** 사람이 중간에 판단을 내리는 방식(human-in-the-loop)을 쓰려면 누가 승인할 수 있는지, 사용자에게 언제 무엇을 물을지 정해야 합니다. 나중에 누가 무엇을 승인했는지도 확인할 수 있어야 합니다.
- **릴리스할 때도 비용을 확인합니다.** 모델을 호출하거나 실패한 작업을 재시도할 때마다 비용이 듭니다. 분기별로 비용을 검토하더라도 릴리스할 때 한 번 더 살펴봐야 합니다.
- **트레이스를 디버깅과 제품 분석에 활용합니다.** 사용자가 무엇을 요청했는지, 어디에서 막혔고 어떤 결과를 바로잡았는지 트레이스에 남습니다. 이 기록으로 다음에 개선할 부분을 찾을 수 있습니다.

평가나 트레이스 수집에 필요한 기능을 팀에서 전부 만들 필요는 없습니다. LangSmith, AgentCore, Temporal 같은 도구도 있습니다. 어떤 도구를 쓰든 누가 평가 결과를 살피고 어느 작업에 승인을 받을지, 비용은 어떻게 관리할지 정하는 건 팀의 몫입니다. 개발할 때부터 정해 두면 문제가 터질 때마다 대응 절차부터 짤 필요가 없습니다.

---

릴리스 노트에 "no code changes"라고 적힌 주에도 에이전트의 답은 바뀔 수 있습니다. 지난주와 이번 주의 트레이스를 나란히 놓고 보면 어느 대목에서 답이 달라졌는지 짚어 볼 수 있습니다. 그 사례를 평가셋에 넣어 두면 다음 버전을 배포할 때 문제를 고쳤는지도 확인할 수 있습니다.
