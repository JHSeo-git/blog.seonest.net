# Ontologies for Agents

<PostMeta createdAt={metadata.openGraph.publishedTime} />

에이전트가 비슷한 장애 기록을 찾아냈더라도, 그 기록만으로는 이번 장애의 원인을 어디서부터 찾아야 할지 알 수 없습니다. "게이트웨이에서 타임아웃이 발생했고 롤백으로 해결했다"라는 요약만 보고서는 지금도 롤백이 필요한지 판단할 수 없습니다. 당시에 무엇을 관측했는지, 그리고 어떤 근거로 원인을 좁혀 나갔는지도 함께 알아야 합니다.

Netflix의 Prasanna Vijayanathan과 Renzo Sanchez-Silva는 배포 기록, 로그, 장애 기록, 그리고 사람들이 나눈 논의를 한 지식 그래프로 연결한 사례를 소개했습니다. 지식 그래프는 대상과 대상 사이의 관계를 함께 저장하므로, 여러 시스템에 흩어져 있던 정보를 한 번에 조회할 수 있습니다. 이 시스템은 사람이 추론한 내용을 기록하고, 각 가설에 증거와 신뢰도를 붙여 둡니다. 가설마다 붙은 증거가 바로 앞에서 말한 "당시에 무엇을 관측했고, 어떤 근거로 원인을 좁혀 나갔는지"에 해당합니다. 이 글에서는 Netflix가 이 지식 그래프를 어떻게 구성했는지 살펴보고, 이런 기록을 에이전트가 이번 장애와 비교해 볼 수 있는 형태로 전달하는 방법을 정리해 보겠습니다.

## Netflix가 온톨로지를 만든 이유

Netflix는 여러 관측 도구를 함께 사용하고, 도구마다 담고 있는 정보가 다릅니다. 텔레메트리 플랫폼인 Atlas에는 애플리케이션의 시계열 데이터가 쌓이고, 알림 시스템인 Radar에는 알림 이력이 쌓입니다. 온콜 순번은 PagerDuty에서, 배포 이력은 Spinnaker에서 관리합니다. 문제는 이 도구들이 같은 대상을 각각 애플리케이션, 서비스, 클러스터처럼 서로 다른 이름으로 부른다는 점입니다.

아래는 온톨로지가 없을 때 이 정보들이 어떤 모습인지 보여 주는 가상의 예시입니다. 세 기록은 모두 같은 게이트웨이의 기록입니다. 그런데 도구마다 필드 이름도 다르고 값을 표기하는 방식도 다릅니다.

```text
# 배포 도구의 기록
{ "application": "apigateway", "region": "us-east-1", "version": "2024.10.3" }

# 알림 도구의 기록
{ "service": "api-gateway-prod", "alert": "latency_p99_high" }

# 장애 관리 도구의 기록
{ "id": "INC-5377", "affected_cluster": "api-gw-useast1", "severity": "SEV 2" }
```

위 세 기록이 같은 게이트웨이에 대한 기록이라는 것은 값만 봐서는 알 수 없습니다. `apigateway`, `api-gateway-prod`, `api-gw-useast1`이 같은 서비스라는 사실은 이 서비스를 잘 아는 몇몇 사람만 알고 있습니다. 그래서 여러 도구의 기록을 맞춰 보며 장애 원인을 찾으려면 그 사람들에게 물어볼 수밖에 없습니다. 이렇게 장애 대응이 소수의 사람에게 의존하면, 그 사람들이 바쁘거나 자리에 없을 때 대응도 함께 늦어집니다.

에이전트에게 이 기록을 그대로 맡기기는 더 어렵습니다. 에이전트는 세 이름이 같은 서비스인지 물어볼 사람도 없어서, 이름만 보고 짐작할 수밖에 없습니다. 그러면 이름이 비슷하다는 이유로 서로 다른 서비스를 같은 서비스로 묶을 수도 있고, 반대로 같은 서비스를 서로 다른 서비스로 나눠 볼 수도 있습니다. 이처럼 맥락이 부족한 AI가 사실이 아닌 내용을 그럴듯하게 만들어 내는 현상을 환각(hallucination)이라고 부릅니다.

Netflix는 이 문제를 해결하려고 온톨로지를 만들었습니다. 온톨로지는 다루는 대상에 어떤 종류(타입)가 있는지, 각 타입이 어떤 속성을 가지는지, 그리고 타입끼리 어떤 관계를 맺을 수 있는지를 미리 정해 둔 것입니다. 예를 들어 "우리 운영 환경에는 애플리케이션과 장애가 있고, 장애는 애플리케이션에 영향을 줄 수 있다"라는 내용을 사람도 기계도 읽을 수 있게 적어 두면 그것이 온톨로지입니다.

Netflix는 이 온톨로지를 자체 형식 대신 W3C의 표준 형식으로 작성했습니다.

> **W3C란?** W3C(World Wide Web Consortium)는 웹 기술의 표준을 정하는 국제 단체입니다. 웹을 처음 만든 팀 버너스리가 1994년에 세웠고, HTML과 CSS의 표준도 이곳에서 정합니다. W3C가 공식 표준으로 확정한 문서는 권고안(Recommendation)이라고 부릅니다.
>
> 버너스리는 웹에 있는 정보를 사람뿐 아니라 기계도 이해할 수 있도록 만들자는 구상을 내놓았는데, 이 구상을 시맨틱 웹(Semantic Web)이라고 부릅니다. 이 글에서 다루는 RDF, OWL, SPARQL, SHACL은 모두 시맨틱 웹을 위해 만들어진 표준입니다. RDF는 1999년, OWL은 2004년, SPARQL은 2008년, SHACL은 2017년에 권고안이 되었습니다. 오래전부터 쓰여 온 표준이라서, 이 표준들을 지원하는 데이터베이스와 라이브러리도 이미 많이 나와 있습니다.

## 온톨로지를 구성하는 요소

Netflix의 온톨로지는 여러 요소가 역할을 나누어 맡는 구조입니다. 각 요소의 원래 이름과 역할은 다음과 같습니다.

- **RDF**(Resource Description Framework): 모든 사실을 주어, 술어, 목적어의 세 부분으로 기록하는 데이터 모델입니다.
- **IRI**(Internationalized Resource Identifier)와 접두사: 대상과 관계에 서로 겹치지 않는 고유한 이름을 붙이는 방법입니다. IRI는 W3C가 아니라 인터넷 표준화 기구인 IETF가 정한 표준(RFC 3987)이며, RDF는 이름을 붙일 때 이 IRI를 사용합니다.
- **Turtle**(Terse RDF Triple Language): RDF 데이터를 사람이 읽을 수 있는 텍스트 파일로 저장하는 문법입니다.
- **OWL**(Web Ontology Language): 사용할 수 있는 타입과 관계를 정의하는 언어입니다.
- **SHACL**(Shapes Constraint Language): 데이터가 정해 둔 규칙을 지키는지 검사하는 언어입니다.
- **SPARQL**(SPARQL Protocol and RDF Query Language): 그래프에서 필요한 정보를 조회하는 쿼리 언어입니다. 이름 안에 자기 이름이 다시 들어가는 약어이며, "스파클"이라고 읽습니다.

Netflix는 이 가운데 RDF, OWL, SHACL, SPARQL로 온톨로지를 구성하고, 데이터는 Turtle 형식으로 보관합니다. IRI는 RDF에 포함된 개념이지만, 처음 접하면 낯설 수 있어서 따로 설명합니다.

### 왜 RDF로 데이터를 표현할까요

데이터를 표현하는 방법에는 RDF 말고도 관계형 데이터베이스의 테이블이나 JSON 같은 문서 형식이 있습니다. 세 방식이 여러 도구의 데이터를 다룰 때 어떻게 다른지 비교하면 다음과 같습니다.

| 비교 항목                      | 관계형 테이블                        | JSON 문서                                                         | RDF                                                         |
| ------------------------------ | ------------------------------------ | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| 데이터의 구조                  | 테이블마다 정해진 컬럼               | 도구(배포 도구, 알림 도구 등)마다 따로 정한 필드 이름과 중첩 구조 | 모든 사실을 주어·술어·목적어 세 부분으로 적은 한 줄(트리플) |
| 새로운 종류의 관계를 추가할 때 | 스키마를 바꿔 컬럼이나 테이블을 추가 | 스키마 변경 없이 문서에 필드를 추가                               | 스키마 변경 없이 새 술어로 한 줄 추가                       |
| 여러 출처의 데이터를 합칠 때   | 공통 키를 맞춘 뒤 조인               | 도구마다 필드와 값을 맞추는 변환 코드 작성                        | 같은 이름을 쓰면 그대로 연결                                |
| 대상의 이름                    | 데이터베이스 안에서만 유효한 기본 키 | 도구마다 다르게 적은 문자열                                       | 어디서나 고유한 IRI                                         |

JSON은 형식이 자유로워서 필드 이름과 구조를 도구마다 다르게 정할 수 있습니다. 앞의 게이트웨이 예시에서도 세 도구가 같은 게이트웨이를 각각 `application`, `service`, `affected_cluster` 필드에 적었고, 값도 `apigateway`, `api-gateway-prod`, `api-gw-useast1`로 모두 달랐습니다.

필드의 위치가 다를 수도 있습니다. 아래 두 기록은 같은 서비스 이름을 담고 있습니다.

```text
# 도구 A
{ "service": "api-gateway-prod" }

# 도구 B
{ "target": { "service": { "name": "api-gateway-prod" } } }
```

도구 A에서는 `service` 필드를 바로 읽으면 되지만, 도구 B에서는 `target` 안의 `service` 안에 있는 `name`까지 찾아 들어가야 합니다. 이렇게 객체 안에 객체를 넣는 방식을 중첩 구조라고 합니다.

그래서 여러 도구의 기록을 합치려면, 도구마다 다른 필드 이름과 위치를 한 가지 형식으로 바꿔 주는 코드가 필요합니다. RDF에서는 모든 데이터를 처음부터 주어·술어·목적어라는 한 가지 형태로 적습니다. 그래서 같은 대상을 같은 이름으로 부르기만 하면, 출처가 다른 데이터도 따로 맞춰 줄 필요 없이 바로 연결됩니다.

Netflix에게 필요했던 것도 바로 이것입니다. 구조와 이름이 제각각인 여러 도구의 데이터를 서로 연결해야 했고, 이런 일에는 RDF가 잘 맞습니다. RDF와 함께 쓰는 타입 정의(OWL), 검증(SHACL), 조회(SPARQL) 표준도 이미 갖춰져 있습니다. 다만 한 서비스 안에서 구조가 정해진 데이터를 빠르게 읽고 쓰는 일에는 지금도 관계형 데이터베이스가 더 낫습니다.

아래에서는 요소마다 온톨로지를 도입하기 전의 원래 모습과 도입한 뒤의 모습을 예시로 비교합니다. 원래 모습으로 든 예시는 모두 설명을 위한 가상의 예시입니다.

### 1. RDF: 사실을 주어·술어·목적어로 기록하는 방식

RDF에서는 모든 사실을 주어, 술어, 목적어의 세 부분으로 나누어 기록하고, 이렇게 기록한 한 줄을 트리플이라고 부릅니다. 예를 들어 "api-gateway는 Team Bedrock이 담당한다"라는 사실에서는 api-gateway가 주어, 담당 관계(ownedBy)가 술어, Team Bedrock이 목적어가 됩니다. 아래는 Netflix가 소개한 예시입니다.

```text
api-gateway   rdf:type       ops:Application .
api-gateway   ops:ownedBy    "Team Bedrock" .
api-gateway   ops:deployedIn "us-east-1" .

INC-5377      rdf:type       ops:Incident .
INC-5377      ops:affects    api-gateway .
INC-5377      ops:severity   "SEV 2" .
```

위 예시는 모두 여섯 줄이고, 한 줄이 사실 하나를 나타냅니다. 각 줄 끝의 마침표(`.`)는 트리플 하나가 끝났다는 표시입니다. api-gateway를 담당하는 팀은 원래 소프트웨어 카탈로그에, api-gateway가 배포된 리전은 Spinnaker에, 장애 정보는 장애 관리 도구에 따로 저장되어 있었습니다. 트리플로 바꾸면 출처가 다른 정보도 모두 같은 형식으로 적히기 때문에, 한 그래프에 그대로 모을 수 있습니다. 그래프에서 주어와 목적어는 점(노드)이 되고, 술어는 두 점을 잇는 선(엣지)이 됩니다.

**원래의 모습과 비교하기**

앞에서 본 도구별 JSON 기록과 트리플을 나란히 놓으면 차이가 분명해집니다.

| 원래의 기록 (도구별 JSON)                                       | 트리플                                     |
| --------------------------------------------------------------- | ------------------------------------------ |
| 배포 도구: `"application": "apigateway", "region": "us-east-1"` | `api-gateway ops:deployedIn "us-east-1" .` |
| 장애 관리 도구: `"affected_cluster": "api-gw-useast1"`          | `INC-5377 ops:affects api-gateway .`       |
| 장애 관리 도구: `"severity": "SEV 2"`                           | `INC-5377 ops:severity "SEV 2" .`          |

JSON 기록은 도구마다 필드 이름과 구조가 다르기 때문에, 두 도구의 데이터를 합치려면 한쪽 구조를 다른 쪽 구조로 바꾸는 변환 코드가 필요합니다. 연결할 도구가 늘어날수록 이런 변환 코드도 함께 늘어납니다. 반면 트리플은 어느 도구에서 왔든 형태가 같습니다. 예를 들어 온콜 도구를 새로 연결한다면, 그 도구의 기록을 트리플로 바꿔 아래처럼 한 줄 추가하기만 하면 됩니다. 여기서 `ex:`는 설명을 위해 지어낸 이름입니다.

```text
# 온콜 도구의 원래 기록
{ "service_id": "PGW01", "escalation_policy": "gateway-oncall" }

# 트리플로 바꾼 기록
api-gateway   ex:onCallRotation   "gateway-oncall" .
```

### 2. IRI와 접두사: 이름이 겹치지 않게 하는 방법

예시에 나온 `rdf:type`, `ops:Application`에서 콜론 앞에 붙은 부분은 접두사입니다. RDF에서는 대상과 관계의 이름을 웹 주소와 비슷한 형태의 전체 식별자(IRI)로 적습니다. 매번 전체 주소를 쓰기는 번거롭기 때문에, 앞부분을 접두사로 줄여서 씁니다. 예를 들어 `rdf:type`은 `http://www.w3.org/1999/02/22-rdf-syntax-ns#type`을 줄인 표기이고, "이 대상의 타입은 무엇이다"라는 의미로 W3C가 미리 정의해 둔 술어입니다.

같은 접두사 아래에 묶인 이름의 집합을 네임스페이스라고 부릅니다. Netflix의 온톨로지는 운영 도메인을 하나씩 담당하는 열두 개의 네임스페이스로 구성되어 있습니다.

**원래의 모습과 비교하기**

이름을 단순한 문자열로만 다루면, 두 기록이 같은 대상의 기록인지 문자열을 비교해서 판단해야 합니다. 예를 들어 `apigateway`, `api-gateway-prod`, `api-gw-useast1`이 같은 서비스인지 확인하려면, 아래처럼 이름을 비교하는 함수를 따로 만들어야 합니다.

```python
def same_service(a, b):
    def normalize(name):
        return name.lower().replace("-prod", "").replace("gw", "gateway").replace("-", "")
    return normalize(a) == normalize(b)

same_service("apigateway", "api-gateway-prod")  # True
same_service("apigateway", "api-gw-useast1")    # False: 리전 표기가 붙어 있어 놓칩니다
```

이런 규칙은 새로운 표기 방식이 나올 때마다 늘어나고, 그래도 빠지는 경우가 생깁니다.

IRI를 쓴다고 이 문제가 저절로 사라지지는 않습니다. 데이터를 넣는 쪽에서 `app:api-gateway` 대신 `app:api-gateway-prod`를 적으면, 그래프에는 서로 다른 대상 두 개가 생깁니다. RDF는 두 IRI가 같은 대상인지 알지 못합니다.

그래서 Netflix는 데이터를 그래프에 저장하기 전에 이름부터 확인합니다. 이때 소프트웨어 카탈로그를 기준으로 삼습니다. 소프트웨어 카탈로그는 회사의 애플리케이션 이름과 식별자를 모아 둔 목록입니다. 새 애플리케이션 정보가 들어오면 카탈로그에서 그 이름을 찾아 등록된 식별자로 저장하고, 카탈로그에서 찾을 수 없는 이름은 애플리케이션으로 저장하지 않습니다. 그러면 그래프 안에서는 같은 애플리케이션이 항상 같은 식별자로 적히므로, 앞의 `same_service` 같은 함수로 이름을 비교할 필요가 없습니다.

```text
# 배포 도구의 기록
app:api-gateway   ops:deployedIn   "us-east-1" .

# 장애 관리 도구의 기록
inc:INC-5377      ops:affects      app:api-gateway .
```

두 기록 모두 `app:api-gateway`라는 같은 식별자를 쓰므로, 따로 비교하지 않아도 같은 게이트웨이의 기록이라는 것을 바로 알 수 있습니다. 카탈로그와 대조하는 과정은 뒤에서 다시 다룹니다.

### 3. Turtle: RDF를 텍스트 파일로 기록하는 문법

RDF는 데이터를 어떤 구조로 표현할지를 정한 모델입니다. 따라서 실제로 파일에 저장하려면 별도의 문법이 필요하며, Turtle은 그중에서 사람이 읽기 쉬운 텍스트 문법입니다. 앞의 예시는 설명을 위해 간략하게 표기한 것이므로, 이를 Turtle 문법에 맞춰 다시 작성하면 다음과 같습니다. 접두사의 실제 주소는 공개되지 않아서 임의로 적었습니다.

```turtle
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix ops: <https://example.com/ops#> .
@prefix app: <https://example.com/app/> .
@prefix inc: <https://example.com/incident/> .

app:api-gateway  rdf:type        ops:Application ;
                 ops:ownedBy     "Team Bedrock" ;
                 ops:deployedIn  "us-east-1" .

inc:INC-5377     rdf:type        ops:Incident ;
                 ops:affects     app:api-gateway ;
                 ops:severity    "SEV 2" .
```

`@prefix`로 시작하는 줄에서는 접두사를 선언하고, 각 트리플은 마침표(`.`)로 끝냅니다. 세미콜론(`;`)은 앞 줄과 같은 주어로 이어서 적는다는 뜻이므로, 주어를 반복해서 쓰지 않아도 됩니다. 따옴표로 감싼 값은 문자열이고, 접두사가 붙은 값은 다른 대상을 가리키는 이름입니다. 예를 들어 `inc:INC-5377`의 `ops:affects` 값이 `app:api-gateway`이므로, 그래프에서는 두 대상이 선으로 연결됩니다.

Netflix는 데이터를 수집할 때마다 전체 데이터를 Turtle 형식으로 직렬화해서 보관합니다. 사람이 직접 읽을 수 있고 diff로 비교할 수도 있어서, 디버깅에 예상보다 훨씬 유용했다고 합니다.

**원래의 모습과 비교하기**

그래프가 데이터베이스 안에만 있으면, 어제와 오늘 사이에 무엇이 바뀌었는지 보려고 해도 두 시점의 데이터를 각각 조회해서 직접 비교해야 합니다. 그래프를 텍스트 파일로 내보내 두면, 다른 파일처럼 diff로 바뀐 부분을 바로 볼 수 있습니다. 그 파일을 git으로 관리하면 변경 이력도 남습니다. diff와 이력은 텍스트 파일과 git 덕분에 가능하고, Turtle은 그 diff를 읽기 쉽게 만듭니다. RDF를 텍스트로 적는 형식에는 태그가 많은 RDF/XML 같은 형식도 있지만, Turtle은 사실 하나를 대체로 한 줄에 적습니다. 그래서 api-gateway의 담당 팀이 바뀌면 diff에도 그 한 줄만 바뀐 것으로 나타납니다.

```diff
 app:api-gateway  rdf:type        ops:Application ;
-                 ops:ownedBy     "Team Bedrock" ;
+                 ops:ownedBy     "Team Edge" ;
                  ops:deployedIn  "us-east-1" .
```

다만 diff가 이렇게 깔끔하게 나오려면, 파일로 내보낼 때마다 트리플을 항상 같은 순서로 적어야 합니다. 순서까지 맞춰 두면 코드 변경을 리뷰하듯이 그래프의 변경도 확인할 수 있습니다.

### 4. OWL: 사용할 수 있는 타입과 관계를 정의하는 언어

지금까지 본 트리플에서는 `ops:ownedBy`나 `ops:deployedIn` 같은 단어를 술어로 썼습니다. 그런데 RDF에는 어떤 단어를 써야 하는지 정하는 규칙이 없어서, 누군가는 `ownedBy` 대신 `owner`나 `team`이라고 적을 수도 있습니다. OWL은 이렇게 쓸 수 있는 단어를 미리 정의해 두는 언어입니다. OWL로는 어떤 타입(클래스)이 존재하는지, 그리고 어떤 관계(속성)가 어느 타입과 어느 타입을 연결하는지를 정의합니다. OWL로 작성한 정의도 결국 RDF 트리플이므로 Turtle 문법으로 적을 수 있습니다. Netflix는 실제 OWL 정의를 공개하지 않았으므로, 아래는 Netflix가 사용하는 어휘로 구성한 예시입니다.

```turtle
ops:Application  rdf:type  owl:Class .
ops:Incident     rdf:type  owl:Class .

ops:affects      rdf:type     owl:ObjectProperty ;
                 rdfs:domain  ops:Incident ;
                 rdfs:range   ops:Application .
```

이 정의는 "Application(애플리케이션)과 Incident(장애)는 타입이고, affects는 장애에서 애플리케이션으로 향하는 관계이다"라는 뜻입니다. 이렇게 정의해 두면 사람과 에이전트, 그리고 여러 도구가 같은 어휘를 기준으로 데이터를 기록하고 읽을 수 있습니다. 이러한 정의가 개념에 해당하고, `app:api-gateway`처럼 특정한 대상에 관한 트리플은 인스턴스에 해당합니다.

**원래의 모습과 비교하기**

공통으로 쓸 어휘가 정해져 있지 않으면, 그래프에 데이터를 넣는 팀마다 같은 관계를 서로 다른 단어로 기록하게 됩니다.

```text
# A 팀이 넣은 데이터
api-gateway   ex:ownedBy   "Team Bedrock" .

# B 팀이 넣은 데이터
api-gateway   ex:owner     "Team Bedrock" .

# C 팀이 넣은 데이터
api-gateway   ex:team      "Team Bedrock" .
```

세 줄은 모두 같은 사실을 담고 있습니다. 하지만 애플리케이션의 담당 팀을 조회할 때는 `ex:ownedBy`, `ex:owner`, `ex:team`을 모두 조건에 넣어야 합니다. 셋 중 하나라도 빠뜨리면, 그 단어로 기록한 팀의 데이터는 조회 결과에 나오지 않습니다. 도구마다 이름이 달라서 생겼던 문제가 그래프 안에서 다시 생깁니다. OWL로 공식 어휘를 정의해 두면, 데이터를 넣는 팀은 새 단어를 만들지 않고 이미 정의된 `ops:ownedBy`를 찾아 쓸 수 있습니다. 다만 OWL은 정의되지 않은 단어를 쓰지 못하게 막지는 않습니다. 그런 검사는 다음 소절에서 다룰 SHACL이 맡습니다.

### 5. SHACL: 데이터가 규칙을 지키는지 검사하는 언어

OWL로 정의를 만들어 두어도 잘못된 데이터가 들어오는 것을 막을 수는 없습니다. 예를 들어 담당 팀 정보가 빠진 애플리케이션이 들어오더라도, OWL은 이를 아직 알려지지 않은 정보로 간주할 뿐 오류로 처리하지 않습니다. 오히려 `ops:affects` 관계가 붙은 대상을 발견하면, 위에서 작성한 정의에 따라 그 대상을 장애(Incident 타입)로 추론합니다.

데이터를 실제로 검사하려면 SHACL을 사용합니다. SHACL에서는 "이 타입의 대상에는 이 속성이 반드시 하나 있어야 한다"와 같이 데이터가 갖춰야 할 형태(셰이프)를 정의하고, 실제 데이터가 그 형태를 따르는지 확인합니다. 즉, OWL은 단어의 의미를 정의하고, SHACL은 입력된 데이터를 검사합니다.

**원래의 모습과 비교하기**

검사 규칙을 한곳에 모아 두지 않으면, 데이터를 넣는 스크립트마다 검증 코드를 따로 넣어야 합니다.

```python
# 배포 기록을 넣는 스크립트: 담당 팀이 없으면 경고만 남깁니다
if "team" not in record:
    log.warning("team missing: %s", record["application"])

# 장애 기록을 넣는 스크립트: 검증 코드가 없습니다
graph.add(to_triples(record))
```

이렇게 되면 검증 코드가 없는 스크립트로 들어온 데이터는, 담당 팀이 없더라도 아무 경고 없이 그래프에 쌓입니다. SHACL을 사용하면 규칙을 한 번만 선언해 두고, 어느 스크립트로 들어온 데이터든 같은 기준으로 검사할 수 있습니다. 아래 셰이프는 "모든 애플리케이션에는 담당 팀이 하나 이상 있어야 한다"는 규칙을 적은 예시입니다.

```turtle
ex:ApplicationShape
    rdf:type sh:NodeShape ;
    sh:targetClass ops:Application ;
    sh:property [
        sh:path ops:ownedBy ;
        sh:minCount 1 ;
    ] .
```

### 6. SPARQL: 그래프를 조회하는 쿼리 언어

SPARQL은 RDF 그래프를 조회하는 쿼리 언어입니다. SQL이 테이블에서 조건에 맞는 행을 찾는다면, SPARQL은 트리플 형태의 패턴을 작성한 뒤 그 패턴과 일치하는 값을 찾습니다. 아래 쿼리에서 물음표로 시작하는 `?app`과 `?incident`는 아직 알지 못하는 값을 담는 변수입니다. 예를 들어 "us-east-1에서 Team Bedrock이 담당하는 애플리케이션에 영향을 준 장애는 무엇인가?"라는 질문을 SPARQL로 옮기면 다음과 같습니다(접두사 선언은 생략했습니다).

```sparql
SELECT ?incident WHERE {
  ?app      rdf:type       ops:Application ;
            ops:ownedBy    "Team Bedrock" ;
            ops:deployedIn "us-east-1" .
  ?incident rdf:type       ops:Incident ;
            ops:affects    ?app .
}
```

**원래의 모습과 비교하기**

온톨로지가 없을 때 같은 질문에 답하려면, 세 도구를 각각 조회한 뒤 그 결과를 코드에서 직접 이어 붙여야 합니다. 아래는 그 과정을 보여 주는 가상의 코드입니다.

```python
apps = [a for a in catalog.list_apps() if a.owner_team == "Team Bedrock"]
in_region = [a for a in apps if "us-east-1" in deploy_tool.regions(a.name)]
names = {normalize(a.name) for a in in_region}
incidents = [i for i in incident_tool.list_incidents()
             if normalize(i.affected_cluster) in names]
```

이 코드는 도구마다 다른 API를 알아야 하고, 이름을 비교하는 `normalize` 같은 규칙에도 의존합니다. 질문이 조금만 바뀌어도 코드를 다시 작성해야 합니다. 모든 사실이 같은 형태의 트리플로 한 그래프에 모여 있으면, 질문을 위와 같은 쿼리로 옮기기만 하면 됩니다.

### 직접 만들지 않고 표준을 사용한 이유

가장 큰 이유는 이식성입니다. RDF, OWL, SHACL, SPARQL은 명세가 공개되어 있고 여러 구현체가 존재하기 때문에, 모델을 여러 그래프 저장소로 옮겨 가며 사용할 수 있습니다. 반면 자체 그래프 모델을 사용하면, 이후에 그 그래프를 사용하는 사람들이 특정 구현에 묶이게 됩니다.

다만 저장소는 Netflix가 직접 만들었습니다. QuipuDB라는 분산 쿼드 스토어이며, Rust 기반의 임베디드 키-값 데이터베이스인 redb를 바탕으로 합니다. 쿼드는 트리플에 "이 사실이 어느 그래프에 속하는가"라는 정보를 하나 더 붙인 형태입니다. 저장소를 직접 만들었더라도 데이터와 온톨로지가 표준을 따르기 때문에, 나중에 저장소를 바꾸더라도 데이터를 그대로 옮길 수 있습니다. 또한 Turtle 파서나 SHACL 검사기, SPARQL 엔진처럼 이미 공개된 도구를 그대로 활용할 수 있다는 점도 표준을 따른 덕분에 얻는 이점입니다.

## 같은 서비스의 기록인지부터 확인하기

가상의 사례를 하나 들어 보겠습니다. 예전에 게이트웨이를 배포한 뒤 여러 리전에서 타임아웃이 늘어난 적이 있고, 그때는 연결 풀 설정이 원인이어서 롤백으로 해결했습니다. 이번에는 한 리전에서만 타임아웃이 발생했습니다. 예전 분석을 참고하려면, 먼저 두 기록이 같은 게이트웨이의 기록인지 확인해야 합니다.

처음부터 서로 다른 서비스를 같은 서비스로 잘못 묶으면, 그 뒤에 하는 비교도 모두 틀리게 됩니다. 그래서 Netflix는 데이터를 등록할 때 다음 세 가지 규칙을 지킵니다.

- **애플리케이션 타입은 하나만 둡니다.** Netflix 안에서 "서비스"라는 말은 네 가지 서로 다른 대상을 가리키고 있었습니다. 그래서 이 뜻들을 모두 담는 Service 타입을 만들지 않고, 애플리케이션은 `ops:Application` 하나로만 표현합니다.
- **카탈로그에 있는 이름만 등록합니다.** 약 4만 9천 개의 항목이 있는 소프트웨어 카탈로그와 대조해서, 사용자 이름이나 팀 이름처럼 검증되지 않은 문자열은 애플리케이션으로 등록하지 않습니다.
- **의존 관계의 수에 상한을 둡니다.** 많이 쓰이는 서비스는 자신을 호출하는 서비스가 수천 개씩 생길 수 있어서, 상한이 없으면 그 서비스 하나가 그래프의 대부분을 차지하게 됩니다.

또한 그래프에 담기는 정보를 두 종류로 나눠서 관리합니다. 하나는 "애플리케이션에는 담당 팀이 있다"처럼 무엇을 어떻게 기록할지 미리 정해 둔 규칙입니다. 앞의 OWL 소절에서 본 정의가 여기에 해당하며, 이를 개념이라고 부릅니다. 다른 하나는 "api-gateway의 담당 팀은 Team Bedrock이다"처럼 실제 대상 하나하나에 대한 기록이고, 이를 인스턴스라고 부릅니다.

개념은 여러 팀이 논의해서 합의해야 바뀌므로 자주 바뀌지 않습니다. 반면 인스턴스는 배포나 장애가 생길 때마다 새로 들어옵니다. 둘을 나눠 두면 규칙은 안정적으로 유지하면서, 자주 바뀌는 기록만 계속 갱신할 수 있습니다.

## 결론과 그 근거를 함께 남기기

예전 분석에는 원인과 해결책 외에도 참고할 만한 내용이 있습니다. 담당자가 어떤 지표를 보고 연결 풀을 의심하게 되었는지, 다른 하위 서비스가 지연되었을 가능성은 어떤 근거로 배제했는지, 그리고 롤백한 뒤 어떤 지표가 회복되었는지 같은 내용입니다. 이런 과정은 로그와 메트릭만 봐서는 알기 어렵고, 주로 사람들이 나눈 대화에 남아 있습니다.

Netflix는 이러한 대화도 그래프에 넣습니다. 예를 들어 메시지 200개, 참여자 50명, 관련 서비스 15개로 이루어진 장애 대응용 Slack 채널을 트리플로 바꿉니다. 이런 대화에는 어떤 가설을 시도했다가 버렸는지, 어떤 완화 조치가 효과가 있었는지, 누가 무엇을 어떤 이유로 알고 있었는지가 담겨 있습니다. 대화가 끝나면 이런 내용은 다시 찾기 어렵기 때문에 그래프에 남겨 둡니다. 실제로 그래프에서 가장 쓸모 있었던 연결(엣지)도 이런 논의에서 나왔습니다.

가설의 근거와 신뢰도는 Netflix의 상관관계 엔진(correlation engine)이 함께 기록합니다. 상관관계 엔진은 장애 무렵에 일어난 여러 이벤트 가운데 서로 관련이 있어 보이는 것들을 찾아서 이어 주는 시스템입니다. Datadog의 Watchdog RCA나 Dynatrace의 Davis AI처럼, 여러 신호를 엮어 장애 원인 후보를 보여 주는 상용 기능을 떠올리면 이해하기 쉽습니다. 예를 들어 "배포를 했고, 그 뒤에 로그 오류가 늘었다"처럼 차례로 이어지는 이벤트의 흐름을 찾는데, 이 흐름을 체인이라고 부릅니다. 엔진이 살펴보는 신호는 로그 오류, 메트릭 이상, 느리거나 실패한 트레이스, 알림, 배포, 설정 변경, 실험, 커밋 등 열세 가지입니다. 로그 오류보다 먼저 발생한 배포나 메트릭 이상보다 먼저 발생한 설정 변경처럼, 인과 관계가 이미 알려진 이벤트 순서에는 처음부터 높은 가중치를 부여합니다. 각 체인은 10분 범위 안에서 이벤트가 얼마나 가까운 시간에 발생했는지와 심각도를 기준으로 점수를 매기고, 신뢰도가 0.6 미만인 체인은 버립니다. 예를 들어 신뢰도가 0.87인 체인은 사람이나 에이전트가 확인해 볼 만한 유력한 가설로 다룹니다. 엔진은 체인을 저장할 때 그 체인을 만드는 데 사용한 그래프 레코드도 함께 저장합니다. 그래서 그래프에는 결론과 함께 증거가 붙은 가설이 남습니다.

앞의 게이트웨이 사례를 Netflix의 표기 방식에 맞춰 가상의 예시로 적으면 다음과 같습니다. 이 중 Netflix가 실제로 사용하는 술어는 `ops:` 접두사가 붙은 것뿐이고, `ex:`로 시작하는 술어는 설명을 위해 지어낸 것입니다.

```turtle
ex:INC-4120  rdf:type       ops:Incident ;
             ops:affects    ex:api-gateway ;
             ex:region      "us-east-1", "eu-west-1" ;
             ex:deployedVersion "2024.10.3" .

ex:hyp-1     rdf:type       ex:Hypothesis ;
             ex:about       ex:INC-4120 ;
             ex:summary     "연결 풀 최대 크기 축소" ;
             ex:status      "confirmed" ;
             ex:evidence    <https://slack.example.com/archives/C01/p1001> .

ex:hyp-2     rdf:type       ex:Hypothesis ;
             ex:about       ex:INC-4120 ;
             ex:summary     "하위 서비스 응답 지연" ;
             ex:status      "ruled-out" ;
             ex:evidence    <https://metrics.example.com/d/downstream-p99> .
```

이 예시에는 당시의 배포 버전과 영향을 받은 리전, 그리고 사람이 확인한 원인과 배제한 가설이 각각의 근거 링크와 함께 기록되어 있습니다. 논의의 원본 메시지와 관측 기록으로 가는 링크를 붙여 두면, 에이전트가 요약 내용의 근거를 직접 다시 확인할 수 있습니다. 모든 대화를 통째로 넘기는 대신 관련된 내용만 추려서 전달하고, 필요할 때 근거를 직접 열어 볼 수 있게 하는 방식입니다.

이제 이번 장애에서 확인한 내용을 옆에 함께 적어 둡니다. 같은 게이트웨이에서 타임아웃이 났다는 점은 예전과 같지만, 이번에는 한 리전에서만 났고 실행 중인 버전도 다릅니다. 연결 풀 지표를 아직 보지 못했다면, 보지 못했다는 것도 그대로 적습니다. 이 정도만 알려 줘도 에이전트는 연결 대기 시간과 풀 사용량부터 조회하고, 문제가 없는 리전과 설정이 다른지도 확인할 수 있습니다. 예전에 롤백으로 해결했다고 해서 이번에도 롤백이 답이라고 알려 주는 것이 아닙니다. 다음에 무엇을 확인해야 할지 좁혀 가는 데 예전 기록을 씁니다.

## 빠진 정보가 있다면 빠졌다는 사실도 알리기

Netflix에서는 인리처(enricher)라는 작은 프로그램 수십 개가 그래프에 데이터를 채웁니다. 인리처는 각자 한 가지 일만 맡습니다. 어떤 인리처는 로그에서 오류 정보를 찾아 넣고, 어떤 인리처는 배포 이력을 찾아 넣습니다. 이 인리처들은 정해진 순서에 따라 하나씩 실행됩니다. 그래서 뒤에 실행되는 인리처는 앞에서 넣어 둔 내용을 바탕으로 일할 수 있습니다.

모든 인리처는 같은 틀을 따릅니다. 외부 시스템에서 정리되지 않은 데이터를 읽어 오고, 그 데이터를 분석한 뒤, 타입이 정해진 트리플로 그래프에 넣습니다. Netflix는 이 틀을 일부러 단순하게 정해 두었고, 코드로 보면 다음과 같습니다.

```python
class Enricher:
    async def _enrich_async(self, ...):
        raw    = await self.fetch(...)      # 1. 노이즈가 섞인 입력 읽기
        result = self.analyze(raw)          # 2. 처리 (확률적일 수 있음)
        graph.add((uri, RDF.type, OPS.X))   # 3. 타입이 지정된 트리플 내보내기
        graph.add((uri, OPS.pred, Literal(result.value)))
        return EnrichmentResult(success=True, triples_added=count)
```

인리처가 그래프에 넣는 결과는 다음 세 가지 조건을 항상 지켜야 합니다.

- 그래프에 넣는 모든 대상에는 타입(`rdf:type`)이 있어야 합니다.
- 모든 대상의 이름(IRI)은 같은 규칙으로 지어야 합니다.
- 애플리케이션(`ops:Application`)은 카탈로그에서 확인된 것만 만들 수 있습니다.

인리처 안에서는 LLM처럼 실행할 때마다 결과가 달라질 수 있는 방법을 써도 됩니다. 다만 그래프에 넣을 때는 이 세 조건을 반드시 통과해야 하므로, 그래프에 쌓이는 데이터의 형태는 늘 일정하게 유지됩니다.

인리처가 메트릭, 로그, 이벤트 같은 외부 시스템을 호출하다 보면 응답이 늦거나 실패할 때도 있습니다. Netflix는 이럴 때도 전체 작업을 멈추지 않고, 가져올 수 있는 데이터만으로 계속 진행합니다(best-effort). 외부 시스템 하나가 느리면 그래프에 들어가는 정보가 조금 줄어들 뿐, 그래프를 채우는 작업은 끝까지 진행됩니다. 이때 이번 장애와 관련된 배포 이력을 가져오지 못했다면, 에이전트에게 넘기는 자료에도 그 사실을 적어 두어야 합니다. 조회에 실패했다는 것과 마지막으로 조회에 성공한 시각을 함께 적습니다. 그렇지 않으면 에이전트는 배포 기록을 가져오지 못한 것인지, 실제로 배포가 없었던 것인지 구분할 수 없습니다.

인리처를 실행하는 순서도 결과에 영향을 줍니다. Netflix는 인리처를 동시에 실행하지 않고 하나씩 차례로 실행합니다. 한 인리처가 그래프를 불러와 트리플을 추가하고 다시 저장하면, 그다음 인리처가 같은 과정을 이어 갑니다. 이렇게 하면 두 가지 이점이 있습니다. 먼저 여러 인리처가 같은 그래프를 동시에 고치다가 서로의 결과를 덮어쓰는 것 같은 경쟁 상태(race condition) 문제가 생기지 않습니다. 그리고 뒤의 인리처가 앞에서 넣은 결과를 활용할 수 있어서 결과가 더 정확해집니다. 병렬로 처리할 때보다 느려지기는 하지만, Netflix는 그만한 가치가 있다고 판단했습니다. 게이트웨이 사례라면, 먼저 이 기록이 어느 서비스의 것인지 확정한 다음에 그 서비스의 배포 기록과 지표를 연결하는 식입니다.

LLM이 내놓는 결과도 타입으로 제한합니다. LLM은 어떤 문장이든 만들어 낼 수 있지만, 그래프에는 정해진 타입과 값에 맞는 트리플만 넣을 수 있습니다. 여러 원칙 가운데 Netflix가 가장 중요하게 지키는 원칙입니다. 예를 들어 Slack 스레드를 분류할 때는 모델이 고를 수 있는 값이 다음처럼 미리 정해져 있습니다.

```text
# 모델은 아래 값 중에서만 고를 수 있습니다
category  IN ["incident", "question", "discussion", "decision"]
sentiment IN ["positive", "neutral", "negative", "urgent"]

# 그래프에는 이렇게 들어갑니다
thread:123  slack:category          "incident" .
thread:123  slack:isIncidentRelated "true"^^xsd:boolean .
```

에이전트에게 넘기는 자료에도 이런 규칙을 둘 수 있습니다. 앞의 게이트웨이 예시에서는 가설마다 `ex:status`에 "confirmed"(확인됨)나 "ruled-out"(배제됨) 같은 상태를 적고, `ex:evidence`에 근거 링크를 붙였습니다. 그런데 상태가 빠져 있거나 두 개가 함께 적힌 가설, 근거 링크가 하나도 없는 가설은 에이전트가 믿고 쓰기 어렵습니다. 이런 가설이 자료에 섞이지 않도록 SHACL로 미리 검사할 수 있습니다. 검사 규칙을 셰이프로 적으면 다음과 같습니다.

```turtle
ex:HypothesisShape
    rdf:type sh:NodeShape ;
    sh:targetClass ex:Hypothesis ;
    sh:property [
        sh:path ex:status ;
        sh:in ( "confirmed" "investigating" "ruled-out" ) ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
    ] ;
    sh:property [
        sh:path ex:evidence ;
        sh:minCount 1 ;
    ] .
```

다만 SHACL은 필요한 항목이 빠짐없이 들어 있는지만 확인할 뿐, 그 내용이 사실인지는 알지 못합니다. 원인 분석이 맞는지는 따로 확인해야 합니다.

표준을 따르더라도 저장소마다 동작이 똑같지는 않습니다. 데이터는 다른 저장소로 그대로 옮길 수 있지만, 추론이나 검증 기능을 어디까지 지원하는지는 저장소마다 다릅니다. 저장소를 바꿀 때는 이런 기능이 그대로 동작하는지 확인해 봐야 합니다.

## 온톨로지를 바꿀 때도 코드처럼 리뷰하기

온톨로지에는 여러 가지 판단 기준이 들어 있습니다. 예를 들어 이름이 다른 두 기록을 같은 서비스의 기록으로 볼지 말지, 여러 가설 가운데 어떤 것을 장애 원인으로 인정할지 같은 기준입니다. 이런 기준을 하나만 바꿔도 에이전트에게 건네는 자료가 달라집니다. 그래서 Netflix는 온톨로지를 코드처럼 버전을 관리하고, 테스트와 리뷰를 거쳐 PR로 바꾸라고 권합니다. 에이전트에게 넘길 자료를 만드는 규칙을 고칠 때도 마찬가지입니다. 고치기 전에 이미 정리해 둔 장애 사례를 새 규칙으로 다시 만들어 보고, 무엇이 달라지는지 확인해 보면 좋습니다.

온톨로지는 에이전트끼리 정보를 주고받는 약속 역할도 합니다. Netflix의 AutoRCA는 장애 원인을 찾는 시스템으로, 각자 한 가지 분석을 맡은 여러 에이전트가 같은 그래프를 함께 씁니다. 예를 들어 트레이스를 분석하는 에이전트가 어떤 애플리케이션(`ops:Application`)에 대해 찾은 내용을 트리플로 적으면, 로그를 분석하는 에이전트는 같은 애플리케이션의 트리플을 읽어서 자기 분석에 씁니다. 두 에이전트는 서로를 몰라도 그래프만 보고 함께 일할 수 있습니다. 새 에이전트를 추가할 때도 그래프에서 쓰는 단어만 알면, 다른 에이전트가 적어 둔 내용을 바로 읽을 수 있습니다.

에이전트는 다음에 확인할 내용이나 취할 조치를 제안하고, 인리처나 온톨로지를 어떻게 바꾸면 좋을지도 제안할 수 있습니다. 하지만 최종 결정은 사람이 내립니다. 검토할 제안이 많아지면, 필수 항목이 빠지지 않았는지나 식별자가 올바른지처럼 기계로 확인할 수 있는 부분은 자동으로 검사합니다. 사람은 근거가 충분한지, 실제로 조치했을 때 어떤 영향이 있을지에 집중해서 보면 됩니다. 사람이 판단한 내용을 적을 때는, 이번 장애에서 직접 확인한 것과 아직 짐작일 뿐인 것을 구분해서 적어야 합니다. 예전 분석이 틀렸거나 그사이 환경이 바뀌었다면, 그 사실도 에이전트에게 넘기는 자료에 적어 둡니다.

처음부터 모든 장애를 이렇게 정리할 필요는 없습니다. 작은 사례 하나로 시작해 보면 됩니다.

1. 먼저 앞에서 본 게이트웨이 장애 하나를 고릅니다. 당시 어떤 증거가 있었고 어떤 조치를 했는지를 트리플로 적어서 서로 연결합니다.
2. 다음으로 이번 장애, 즉 한 리전에서만 타임아웃이 난 상황을 같은 방식으로 적어서 예전 기록과 비교할 수 있게 만듭니다. 이때 배포 이력을 가져오지 못한 경우처럼 정보가 빠진 상황도 일부러 넣어 봅니다.
3. 마지막으로 이 자료를 에이전트에게 주고 결과를 살펴봅니다. 에이전트가 어떤 지표나 설정을 더 확인해야 한다고 제안하는지, 그리고 왜 그렇게 생각했는지 근거까지 설명하는지 확인합니다.

이 세 단계만 해 봐도, 지금 가진 기록으로 에이전트에게 얼마나 쓸모 있는 자료를 줄 수 있는지 알 수 있습니다.

## 마치며

에이전트를 잘 활용하려면 데이터부터 정리해 두는 편이 좋습니다. 같은 서비스를 부르는 이름이 여러 개이거나 결론만 있고 근거가 없으면, 에이전트가 그럴듯하지만 틀린 답을 내놓기 쉽습니다. 반대로 이름과 관계가 잘 정리되어 있으면 사람이 일일이 확인하던 일을 에이전트에게 맡겨도 됩니다.

이렇게 정리해 두면 사람도 편해집니다. 이름이 하나로 맞춰지고 근거가 같이 적혀 있으니, 팀에 새로 온 사람도 예전 맥락을 금방 확인할 수 있습니다. 몇 달 뒤에 그때 왜 그렇게 판단했는지 확인할때도 편리합니다. 예전 내용을 기억하는 사람을 찾아다니며 물어볼 필요가 없습니다.

Netflix처럼 온톨로지부터 처음부터 완전한 모습으로 만들 필요는 없습니다. 우리 팀이 다루는 시스템에 무엇이 있는지, 그것들을 서로 어떤 이름으로 부르고 있는지 적어 보는 것만으로도 좋은 출발입니다.
