# ESLint v10 마이그레이션 가이드 정리

<PostMeta createdAt={metadata.openGraph.publishedTime} />

최근 ESLint 공식 문서에서 `Migrate to v10.x` 페이지를 봤습니다. 2026년 4월 21일 기준 [공식 ESLint 마이그레이션 문서](https://eslint.org/docs/latest/use/migrate-to-10.0.0)에 따르면, 업그레이드 전에 Node.js 버전과 설정 방식부터 확인해야 합니다.

<Callout title="Note">
  공식 문서의 주요 변경점을 사용자와 플러그인 작성자, 연동 도구 작성자가 확인할 항목으로 나누었습니다.
</Callout>

## 가장 먼저 확인할 체크리스트

ESLint v10 업그레이드에서 먼저 걸리는 항목은 여섯 가지입니다.

1. Node.js 버전이 `20.19.0+`, `22.13.0+`, `24+` 중 하나인지 확인합니다.
2. 아직 `.eslintrc*` 기반 설정을 쓰고 있다면 `eslint.config.*` 기반 flat config로 옮깁니다.
3. `ESLINT_USE_FLAT_CONFIG=false` 같은 레거시 전환 옵션을 제거합니다.
4. `v10_config_lookup_from_file` 플래그를 쓰고 있다면 모두 제거합니다.
5. `eslint:recommended`를 쓰는 프로젝트라면 새 규칙 3개 때문에 에러가 늘어날 수 있으니 먼저 CI를 돌려 봅니다.
6. 규칙이나 파서, 포매터, 에디터 연동 기능을 직접 만들었다면 개발자용 호환성 변경 사항도 검토합니다.

## 일반 사용자 기준으로 크게 바뀌는 것

### 1. 지원 Node.js 버전이 올라갔습니다

ESLint v10은 더 이상 아래 버전을 지원하지 않습니다.

- `Node.js < 20.19`
- `Node.js v21`
- `Node.js v23`

최소 지원 버전은 `20.19.0`이지만, 사용하는 Node.js의 주 버전에 따라 필요한 최소 버전이 다릅니다. 에디터 확장도 함께 점검해야 합니다. 터미널에서는 새 Node.js를 쓰더라도 에디터의 ESLint 연동 기능이 다른 런타임을 사용하면 문제가 생길 수 있습니다.

Node 업그레이드가 아직 어렵다면 공식 문서도 **당장은 ESLint v9에 머물러도 된다**고 안내합니다.

### 2. `eslint:recommended`에 규칙 3개가 추가됐습니다

새로 들어간 규칙은 세 개입니다.

- `no-unassigned-vars`
- `no-useless-assignment`
- `preserve-caught-error`

기존에 `eslint:recommended`를 사용했다면 v10으로 올린 직후 린트 오류가 늘어날 수 있습니다. 먼저 CI에서 어떤 오류가 생기는지 확인하고, 코드를 수정할지 팀 정책에 맞춰 해당 규칙을 비활성화할지 정하면 됩니다.

### 3. 파일 위치를 기준으로 설정을 찾습니다

v9에서는 `v10_config_lookup_from_file` 플래그로 미리 켤 수 있었던 동작이 v10부터 기본값이 됐습니다.
이제 ESLint는 lint 대상 파일이 있는 디렉터리부터 시작해 위로 올라가며 `eslint.config.*`를 찾습니다.

이 때문에 아래와 같은 설정은 제거해야 합니다.

```bash
# CLI
npx eslint . --flag v10_config_lookup_from_file

# Environment
ESLINT_FLAGS=v10_config_lookup_from_file
```

Node.js API에서도 `new ESLint({ flags: [...] })` 또는 `new Linter({ flags: [...] })`에
`"v10_config_lookup_from_file"`을 넘기면 안 됩니다.

기존처럼 현재 작업 디렉터리(`cwd`)를 기준으로 설정을 찾는다고 가정했다면 영향을 확인해야 합니다. 설정 파일 경로를 직접 지정할 수도 있습니다.

```bash
npx eslint . --config ./eslint.config.mjs
```

모노레포나 패키지별 lint 스크립트라면 특히 꼼꼼히 점검해야 합니다.

### 4. 예전 설정 형식은 더 이상 지원하지 않습니다

`.eslintrc`, `.eslintrc.json` 같은 예전 설정 형식은 v10에서 제거됐습니다. v9에서 임시로 사용하던 `ESLINT_USE_FLAT_CONFIG=false`도 더 이상 동작하지 않습니다. 이제 다음과 같은 flat config 파일을 사용해야 합니다.

- `eslint.config.js`
- `eslint.config.mjs`
- 그 외 공식적으로 지원하는 `eslint.config.*`

사용 중단을 예고했던 `FlatESLint`, `LegacyESLint`도 제거됐으므로 `ESLint`를 사용해야 합니다. 아직 설정을 옮기지 않았다면 [공식 설정 마이그레이션 가이드](https://eslint.org/docs/latest/use/configure/migration-guide)를 참고하면 됩니다.

### 5. JSX 참조가 이제 정상적으로 추적됩니다

이전 ESLint는 `<Card />` 같은 JSX 식별자를 변수 참조로 제대로 다루지 못했습니다. 실제로 사용 중인 값에 `defined but never used` 오류가 나오거나, import를 지워도 `no-undef`가 기대대로 동작하지 않는 경우가 있었습니다.

v10부터는 JSX 식별자도 일반 변수 참조처럼 처리합니다. 기존의 JSX 참조 처리 문제를 보완하려고 추가한 규칙이 있다면, 여전히 필요한지 확인한 뒤 제거할 수 있습니다.

### 6. `eslint-env` 주석은 이제 에러입니다

예전 설정 체계에서는 아래처럼 파일 상단에서 글로벌 환경을 선언하곤 했습니다.

```js
/* eslint-env node */
```

flat config에서는 이 주석을 지원하지 않으며, v10부터는 린트 오류로 보고합니다. 전역 변수 설정은 주석 대신 설정 파일의 `languageOptions.globals`로 옮겨야 합니다.

### 7. TypeScript 설정 파일을 쓴다면 `jiti` 버전도 확인해야 합니다

ESLint 설정 파일을 TypeScript로 작성하고 `jiti`로 불러온다면, `jiti` 버전은 `2.2.0` 이상이어야 합니다. `2.1.2` 이하를 사용 중이라면 함께 올려야 합니다.

## 놓치기 쉬운 호환성 변경 사항

### glob 패턴에서 POSIX 문자 클래스를 인식합니다

ESLint v10은 최신 `minimatch`를 사용해 glob 패턴의 POSIX 문자 클래스를 지원합니다. 예를 들어 `[[:upper:]]`는 대문자에 대응하므로 다음 패턴은 파일 이름이 대문자로 시작하는 `.js` 파일을 찾습니다.

```bash
npx eslint "**/[[:upper:]]*.js"
```

기존 glob 패턴에서 POSIX 문자 클래스로 해석할 수 있는 부분을 단순한 문자열로 취급했다면, 일치하는 파일이 달라질 수 있습니다. `files`와 `ignores`, `globalIgnores()`, CLI 인자를 모두 점검해야 합니다.

### `stylish` 포매터의 색상 출력 기준이 달라졌습니다

`stylish` 포매터는 `chalk` 대신 Node.js의 기본 `styleText`를 사용합니다. 이에 따라 `NO_COLOR`, `NODE_DISABLE_COLORS`, `FORCE_COLOR` 환경 변수도 Node.js와 같은 규칙으로 해석합니다. `--color`, `--no-color` CLI 플래그는 환경 변수보다 우선합니다.

CI 로그의 색상이 달라졌다면 환경 변수와 CLI 플래그부터 확인하면 됩니다.

### 일부 기본 규칙의 옵션 검증이 더 엄격해졌습니다

확인할 변경점은 네 가지입니다.

- `radix`의 `"always"`와 `"as-needed"` 문자열 옵션은 사용 중단이 예고됐습니다. `"always"`를 지정했다면 지워도 동작은 같습니다. `"as-needed"`를 사용했다면 옵션을 지우고 `parseInt()`에 진수를 항상 명시하도록 코드를 바꿔야 합니다.
- `no-shadow-restricted-names`는 이제 `globalThis`도 기본적으로 보호합니다. 같은 이름의 변수를 선언해 기존 이름을 가리는 섀도잉(shadowing)을 허용하지 않습니다.
- `func-names`는 옵션 배열에 허용하지 않는 값이 있으면 설정 오류로 처리합니다.
- `no-invalid-regexp`의 `allowConstructorFlags` 배열에는 중복 항목을 넣을 수 없습니다.

이전에 허용하던 옵션도 v10에서는 설정 오류가 될 수 있습니다.

### `@eslint/js`의 기본 설정에 `name`이 다시 포함됩니다

일반 사용자라면 대부분 신경 쓸 필요가 없습니다.
다만 `@eslint/js` v10과 `FlatCompat`을 같이 쓰고 있다면 `@eslint/eslintrc`도 최신으로 올리는 것이 안전합니다.

## 플러그인이나 규칙, 파서를 만든다면 API도 확인해야 합니다

ESLint 기능을 확장하는 코드를 직접 작성했다면 다음 변경 사항도 확인해야 합니다.

### `RuleTester` 관련 검증이 더 엄격해졌습니다

규칙 위반이 있는 `invalid` 테스트 케이스에서는 `errors`의 `type` 속성이 제거됐습니다. 규칙 위반이 없는 `valid` 테스트 케이스에는 `errors`나 `output`을 넣으면 안 됩니다. 이전에는 무시하던 설정이 v10에서는 테스트 실패의 원인이 됩니다.

### `Program.range`가 나타내는 범위가 바뀌었습니다

추상 구문 트리(AST)의 `Program` 노드에서 `range`는 이제 코드 본문뿐 아니라 앞뒤 주석과 공백을 포함한 전체 소스 텍스트를 가리킵니다. 다음과 같은 코드가 영향을 받습니다.

- `Program.range` 값에 의존하는 규칙
- `Program` 노드에 직접 오류를 보고하는 규칙
- `Program` 노드를 기준으로 앞쪽 주석을 읽는 로직

공식 문서는 `Program`에 직접 오류를 보고했다면 대상을 `node.body[0] ?? node`로 조정하라고 권합니다. 그래야 `/* eslint-disable */` 지시문이 계속 기대대로 동작합니다.

### 자동 수정 메서드에는 문자열을 전달해야 합니다

아래 메서드에 전달하는 `text` 값이 문자열이 아니면 v10부터 `TypeError`가 발생합니다.

- `insertTextBefore`
- `insertTextBeforeRange`
- `insertTextAfter`
- `insertTextAfterRange`
- `replaceText`
- `replaceTextRange`

암묵적 형변환에 의존했다면, 메서드에 전달하기 전에 값을 명시적으로 문자열로 변환해야 합니다.

### 사용 중단을 예고했던 `context` 멤버가 제거됐습니다

v9에서 사용 중단을 예고한 항목이 v10에서 삭제됐습니다.

```js
// before
context.getCwd()
context.getFilename()
context.getPhysicalFilename()
context.getSourceCode()
context.parserOptions
context.parserPath

// after
context.cwd
context.filename
context.physicalFilename
context.sourceCode
context.languageOptions
context.languageOptions?.parserOptions
```

`context.parserPath`는 대체 API가 없습니다.

일부 메서드는 `eslint-transforms`의 `v9-rule-migration`으로 자동 변환할 수 있습니다. 속성 변경은 직접 확인해야 합니다.

### 사용 중단을 예고했던 `SourceCode` 메서드도 제거됐습니다

제거된 메서드는 네 개입니다.

- `getTokenOrCommentBefore()`
- `getTokenOrCommentAfter()`
- `isSpaceBetweenTokens()`
- `getJSDocComment()`

대신 이렇게 바꿔 쓰면 됩니다.

```js
sourceCode.getTokenBefore(node, { includeComments: true })
sourceCode.getTokenAfter(node, { includeComments: true })
sourceCode.isSpaceBetween(first, second)
```

`getJSDocComment()`는 별도 대체 메서드가 없습니다.
호환 계층이 필요하다면 공식 문서가 언급한 `@eslint/compat`도 검토할 만합니다.

### 파서와 `ScopeManager`를 직접 구현했다면 수정이 필요합니다

직접 구현한 `ScopeManager`는 코드에서 선언한 전역 `var`, `function`에 대한 참조를 자동으로 해석해야 합니다. `addGlobals(names: string[])` 인스턴스 메서드도 제공해야 합니다. 자체 파서를 유지보수한다면 함께 확인해야 합니다.

## 통합 도구 작성자도 API 변경을 봐야 합니다

Node.js API를 사용하는 에디터 연동 기능이나 포매터, 자체 린트 실행 도구가 있다면 다음 변경 사항도 확인해야 합니다.

### `LintMessage.nodeType`이 제거됐습니다

사용 중단을 예고했던 `LintMessage.nodeType`이 v10에서 제거됐습니다. 직접 만든 포매터나 에디터 표시 기능에서 `message.nodeType`을 사용한다면 해당 의존성을 제거해야 합니다.

### 설정 탐색과 glob 처리 방식도 확인해야 합니다

ESLint를 호출하는 연동 도구도 다음 변경 사항의 영향을 받습니다.

- 설정 파일을 찾는 방식의 변경
- `.eslintrc*` 지원 제거
- glob 패턴의 POSIX 문자 클래스 처리

연동 도구 내부에서 CLI 옵션이나 API의 `flags` 값을 구성한다면, 이전 동작을 전제로 한 코드가 남아 있는지 확인해야 합니다.

## 제가 업그레이드한다면 이렇게 하겠습니다

1. Node.js 버전을 맞춥니다.
2. `.eslintrc*` 설정을 `eslint.config.*`로 옮깁니다.
3. `ESLINT_USE_FLAT_CONFIG`, `v10_config_lookup_from_file` 같은 전환기 옵션을 제거합니다.
4. `eslint:recommended`의 새 규칙으로 어떤 오류가 생기는지 CI에서 확인합니다.
5. JSX 참조를 보완하던 규칙과 `eslint-env` 주석, 영향을 받는 glob 패턴을 정리합니다.
6. 규칙과 파서, 포매터, 에디터 연동 기능을 직접 만들었다면 제거된 API를 사용하는지 별도로 확인합니다.

<Callout title="Caution">
  Node 업그레이드나 flat config 이전이 아직 준비되지 않았다면, ESLint v10으로 급하게 올리는 것보다
  v9를 유지하면서 선행 작업을 끝내는 편이 더 안전합니다.
</Callout>

## 사용하는 설정과 API를 기준으로 점검합니다

ESLint v10에서는 flat config로의 전환을 마무리하고, 사용 중단을 예고했던 API를 제거했습니다. 일반 사용자는 Node.js 버전과 설정 형식, 새 `recommended` 규칙부터 확인하면 됩니다. 플러그인이나 연동 도구를 유지보수한다면 `context`, `SourceCode`, `RuleTester`, `LintMessage`에서 제거된 항목도 점검해야 합니다.

업그레이드할 때는 [Migrate to v10.x](https://eslint.org/docs/latest/use/migrate-to-10.0.0)와 [Configuration Migration Guide](https://eslint.org/docs/latest/use/configure/migration-guide)를 함께 참고하면 됩니다.
