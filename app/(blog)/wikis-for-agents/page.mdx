# Wikis for Agents

<PostMeta createdAt={metadata.openGraph.publishedTime} />

제 레포에는 `openwiki/`라는 디렉터리가 있습니다. 여기에 모아 둔 마크다운 문서를 가장 자주 읽는 건 코딩 에이전트입니다. 예전 같으면 문서 고치는 일부터 뒤로 미뤘을 텐데, 요즘은 꽤 공을 들입니다. 오늘 틀린 데를 고쳐 두면 다음 세션에서 바로 티가 나기 때문입니다.

## 읽지 않는 위키는 고치는 사람도 없습니다

검색해서 겨우 찾은 문서가 지금 코드와 다르면 다음부터는 그 문서를 잘 열어 보지 않습니다. 틀린 줄 알아도 당장 내 일을 마쳐야 하니 그냥 넘어가기 쉽습니다. 그렇게 읽는 사람도 고치는 사람도 줄면서 위키에는 오래된 설명만 남습니다.

구글도 같은 문제를 겪었습니다. [『Software Engineering at Google』의 문서화 챕터](https://abseil.io/resources/swe-book/html/ch10.html)를 보면, 초기에 사내 위키 GooWiki에 모아 둔 문서 가운데 담당자가 없는 문서는 제때 고치는 사람이 없었습니다. "문서를 고칠 수 있는 사람과 문서를 사용하는 사람이 달랐다"는 회고도 있습니다. 구글은 g3doc이라는 프레임워크를 써서 문서와 코드를 같은 저장소에서 버전 관리하기로 했습니다. 덕분에 코드를 바꿀 때 관련 문서도 함께 고칠 수 있었습니다.

이 책에는 문서 쓰기가 자꾸 뒷전으로 밀리는 이유도 나옵니다. 한 번 써 둔 문서를 나중에 수백 번 읽을 수도 있지만, 자료를 정리하고 글을 쓸 시간은 지금 내야 합니다. 쓰는 사람은 정작 누가 얼마나 도움을 받았는지 알기 어렵습니다.

## 이제 문서는 에이전트가 읽습니다

코딩 에이전트는 세션을 열 때마다 CLAUDE.md나 AGENTS.md 같은 문서를 읽습니다. 6만 개가 넘는 오픈소스 레포에서 [AGENTS.md](https://agents.md/)를 씁니다. [Anthropic의 가이드](https://code.claude.com/docs/en/best-practices)도 CLAUDE.md를 "코드처럼 다루라"고 말합니다. 내용을 리뷰하고, 불필요한 내용을 주기적으로 지우고, 수정한 뒤에는 에이전트의 행동이 실제로 달라지는지 확인하라고 권합니다.

문서마다 담당자를 정하고 리뷰를 거치는 g3doc의 원칙을 에이전트가 읽는 문서에도 적용하는 것입니다.

위키를 관리하기도 한결 수월해졌습니다. 올해 4월 Karpathy는 [LLM으로 개인 위키를 관리해 본 경험](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)을 공유했습니다. 그가 특히 힘들어한 일은 자료를 읽고 생각하는 일보다도 장부 정리(bookkeeping)였습니다. 내용 하나가 바뀌면 파일 열다섯 개를 열어 링크를 고치고 낡은 설명을 지워야 했습니다. 이런 반복 작업은 LLM에 맡길 수 있습니다.

위키를 관리하기 위한 표준과 도구도 나왔습니다. 6월에는 Google Cloud가 [OKF(Open Knowledge Format) v0.1](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)을 공개했습니다. 지식을 여러 마크다운 파일에 나눠 담고, 각 파일에 YAML 프런트매터를 넣는 규격입니다. SDK나 레지스트리를 두지 않고 "플랫폼이 아니라 포맷"을 내세웁니다. 7월에는 LangChain이 [openwiki](https://github.com/langchain-ai/openwiki)를 내놓았습니다. 위키를 생성한 뒤에도 계속 관리하는 에이전트 CLI로, v0.2.0부터 OKF를 채택했습니다.

검색과 위키를 비교해 보면 영수증과 가계부가 떠오릅니다. 궁금한 게 생길 때마다 영수증 더미를 뒤져 답을 찾는 쪽이 검색 기반 접근(RAG)에 가깝습니다. 가계부를 써 두면 다음번에는 장부만 펴면 됩니다. 새 영수증이 생겨도 한 줄만 보태면 되고요. Karpathy는 이를 두고 "지식은 한 번 컴파일되고 이후에는 최신으로 유지된다"고 했습니다.

물론 가계부에 금액을 더하는 것보다 위키를 고치는 데 손이 더 갑니다. 새 자료를 읽고 기존 설명과 맞춰 본 뒤 어디를 고칠지 판단해야 합니다. 이 일을 미루면 위키에 적힌 내용과 실제 코드가 조금씩 어긋납니다.

## 레포 위키는 코드가 바뀔 때 함께 고칩니다

openwiki를 코드 모드로 실행하면 레포의 `openwiki/` 아래에 위키가 생깁니다. 처음 읽을 때는 `quickstart.md`부터 열면 됩니다. 여기까지는 다른 위키 생성기와 비슷합니다. 차이는 그다음에 코드를 고치고 다시 실행할 때 드러납니다.

openwiki는 문서 생성이나 갱신에 성공하면 당시의 git HEAD를 `openwiki/.last-update.json`에 기록합니다. 다음에 실행할 때는 그 이후의 커밋만 읽고, 바뀐 소스가 어떤 문서에 영향을 주는지 확인해 수정 계획을 세웁니다. 프롬프트에도 이렇게 적혀 있습니다. "업데이트는 수술하듯 정밀해야 한다. 새 문단을 더하기보다 낡은 문장 하나를 바꾸는 쪽을 택하라." 바뀐 소스 파일이 다섯 개 미만이면 위키도 한두 페이지만 고치도록 제한하고, 변경이 없으면 수정하지 않습니다. CI에서 정기적으로 실행하도록 설정하면 갱신 내용을 PR로 받을 수 있습니다.

문서 구조는 OKF 형식을 따릅니다. 모든 페이지는 type, title, description, tags를 담은 YAML 프런트매터로 시작합니다. description은 에이전트가 필요한 문서를 검색할 수 있도록 작성합니다. 문서마다 개념 하나를 설명하고, 관련 개념을 다루는 문서에 링크를 겁니다. "A는 B에 디스패치한다", "C는 D를 통해 설정된다"처럼 관계를 설명하는 문장 안에 링크를 넣으면, 개념 사이의 관계와 그 근거를 함께 확인할 수 있습니다.

각 디렉터리의 index.md는 정해진 규칙으로 생성합니다. 항상 같은 결과가 나와야 하는 부분은 LLM에게 맡기지 않았습니다.

저는 CLI 대신 이 워크플로를 [Claude Code 스킬로 포팅](https://github.com/JHSeo-git/openwiki-skill)해서 씁니다. 코딩 에이전트에는 이미 LLM과 파일 도구가 있으므로, 원래 CLI가 프로바이더 API를 호출해 하던 일을 에이전트에게 직접 맡길 수 있습니다. 별도의 API 키나 런타임을 준비할 필요가 없습니다.

여러 레포에 위키를 만들어 보니 소스에서 읽어 낼 수 없는 이야기를 적어 두는 게 특히 도움이 됐습니다. 예를 들어 [claude-codex-imagegen](https://github.com/JHSeo-git/claude-codex-imagegen)의 quickstart에는 제가 왜 이 프로젝트를 시작했는지 적혀 있습니다. API 요금을 따로 내지 않고 구독에 포함된 사용량을 쓰고 싶었고, 그래서 작업을 조율하는 코드가 복잡해지는 쪽을 택했습니다. 소스를 다시 읽는 에이전트는 코드가 복잡하다는 건 알아도 제가 왜 그쪽을 택했는지까지 알 수는 없습니다.

[DeepWiki](https://cognition.com/blog/deepwiki)는 외부 서버에서 위키를 만들어 호스팅해 줍니다. 특정 시점의 코드를 정리한 스냅숏이라 낯선 레포를 처음 읽을 때는 유용하지만, 제 레포의 문서를 계속 관리하는 용도로 쓰기는 어렵습니다. openwiki로 만든 위키는 레포에 커밋하는 마크다운 파일입니다. git 이력이 남고, PR로 리뷰할 수 있으며, 에이전트가 로컬에서 바로 읽을 수 있습니다.

## 개인 위키는 흩어진 지식을 정리해 줍니다

제 개인 자료는 레포 문서보다 찾기가 더 어려웠습니다. 나중에 읽고 싶은 글은 X에서 좋아요를 눌러 뒀고, 클립과 번역은 블로그에 올렸습니다. 노트는 Obsidian과 LLM으로 관리하는 별도 위키에 나뉘어 있었습니다. 네 곳을 뒤져야 하니 지금 무슨 일을 하고 있고 다음에는 뭘 하기로 했는지 한눈에 보이지 않았습니다.

openwiki의 퍼스널 모드를 켜면 `~/.openwiki/wiki`에 개인 위키가 생깁니다. 에이전트가 연결해 둔 로컬 레포와 웹 문서, 피드를 읽고 같은 주제의 내용은 대표 페이지(canonical page) 한 곳에 모아 줍니다.

지금 어디까지 일했는지 보거나 다른 문서를 찾을 때는 quickstart를 엽니다. themes에서는 여러 자료에 공통으로 나오는 내용을, commitments에서는 약속과 할 일을 확인할 수 있습니다. 아직 답을 찾지 못한 질문은 open-questions에 적고, 출처별 페이지에는 근거만 간단히 남깁니다. 프롬프트는 이렇게 자료를 모아 정리한 위키를 "소스 덤프가 아니라 종합 레이어"라고 부릅니다.

개인 위키를 읽을 때 특히 도움이 되는 건 각 내용에 붙은 confidence 라벨입니다. 여러 출처에서 확인한 내용은 confirmed, 한 곳에서만 확인한 내용은 source-backed, 아직 근거가 약한 내용은 watchlist로 표시합니다. 에이전트의 답을 읽으면서도 어디까지 확인된 이야기인지 알 수 있습니다.

LangChain은 이 모드를 [능동적(proactive) 메모리](https://www.langchain.com/blog/introducing-openwiki-brains-general-purpose-wiki-memory-for-agents)라고 소개합니다. 채팅 메모리에는 제가 말해 준 내용이 남습니다. 이 모드에서는 에이전트가 제가 작업하는 레포와 피드를 직접 읽고 위키에 정리합니다. 몇 주 써 보니 새 세션을 열 때부터 차이가 났습니다. 에이전트가 위키를 읽고 지난주에 무엇을 하기로 했는지 이미 알고 있어서, 제가 다시 설명할 필요가 없습니다.

개인 위키를 만들 때부터 지키는 규칙이 하나 있습니다. 회사 일은 로컬 위키에만 적고 그 내용은 어떤 외부 서비스로도 보내지 않습니다. 자료를 한곳에 모으니 무엇을 담을지 정할 때부터 어디로 보낼 수 있는지도 함께 따지게 됐습니다.

## 만든 뒤 관리하지 않은 문서는 성능을 떨어뜨립니다

[ETH 취리히의 연구](https://www.infoq.com/news/2026/03/agents-context-file-value-review/)는 실제 파이썬 과제 138개로 컨텍스트 파일의 효과를 측정했습니다. LLM이 생성한 컨텍스트 파일을 사용하자 성공률은 약 3% 떨어지고 비용은 20% 넘게 올랐습니다. 사람이 쓴 파일도 개선 폭은 4% 남짓이었습니다.

DeepWiki가 있지도 않은 설치 방법을 사실처럼 안내해 [프로젝트 관리자가 공개적으로 항의한 사례](https://blopker.com/writing/12-deepwiki/)도 있습니다. [openwiki의 HN 스레드](https://news.ycombinator.com/item?id=48752949)에는 "LLM 위키의 품질 유지가 생각보다 훨씬 힘들다"는 경험담도 여럿 나옵니다. 장황하고 낡은 문서는 에이전트 성능을 오히려 떨어뜨립니다.

문서를 만들어 놓고 아무도 내용을 확인하거나 고치지 않으면 이런 오류가 그대로 남습니다. openwiki에서는 사람이 INSTRUCTIONS.md에 작업 방향을 적고, 에이전트가 바뀐 코드에 맞춰 문서를 조금씩 고치면 사람이 PR을 읽고 확인합니다.

구글이 GooWiki에서 g3doc으로 옮길 때처럼 문서마다 관리할 사람이 있어야 합니다. 작업 중에 문서를 읽고, 고칠 때는 리뷰를 거쳐야 합니다. 에이전트에게 읽고 갱신하는 일을 맡기더라도 사람이 이 과정을 챙겨야 합니다.

예전에는 문서를 고쳐도 누가 언제 읽을지 몰라 다른 일부터 하곤 했습니다. 요즘은 오늘 고친 문단을 에이전트가 바로 다음 세션에서 읽습니다. 어제까지만 해도 다시 설명해 줘야 했던 일을 오늘은 곧바로 이어 가는 걸 보면, 문서 고치는 데 쓴 시간이 아깝지 않습니다.
