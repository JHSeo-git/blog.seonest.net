# 에이전트도 동료처럼 믿어도 될까?

<PostMeta createdAt={metadata.openGraph.publishedTime} />

Simon Willison은 [블로그](https://simonwillison.net/2026/May/6/vibe-coding-and-agentic-engineering/)에 이렇게 썼습니다. "나는 이제 에이전트가 짠 프로덕션 코드를 한 줄씩 보지 않는다."

## 흐려진 경계

Simon은 혼자 쓸 도구라면 원하는 대로 돌아가는지만 확인해도 괜찮다고 봤습니다. 코드를 들여다보지 않고 쓰는 게 바이브 코딩(vibe coding)입니다. 실서비스에 들어갈 코드라면 이야기가 다릅니다. AI의 도움을 받더라도 일하며 쌓은 경험(25년 동안 개발자로)으로 직접 판단하고 결과에 책임을 졌습니다. Simon은 이런 방식을 에이전틱 엔지니어링(agentic engineering)이라고 불렀습니다.

그런데 에이전트가 맡은 일을 거듭 잘 해내자 Simon도 예전처럼 실서비스 코드를 한 줄씩 확인하지 않게 됐습니다. 가령 Claude Code에 SQL 쿼리를 실행해 결과를 JSON으로 돌려주는 API를 만들어 달라고 하면, 원하는 대로 동작하는 코드가 나옵니다. 테스트와 문서도 함께 작성해 줍니다.

Simon은 다른 팀이 운영하는 이미지 리사이즈 서비스를 예로 들었습니다. 이미지 크기를 바꾸는 데 굳이 그 팀의 Git 저장소까지 열어 볼 일은 드뭅니다. 대개는 문서를 보고 필요한 함수를 호출합니다. 결과가 이상할 때만 소스를 들여다봅니다.

## 문제가 생기면 누가 책임질까요?

옆 팀이 지난 분기에 서비스를 안정적으로 운영했고 다음 분기에도 맡는다고 해 보겠습니다. 문제가 생기면 그 팀에 고쳐 달라고 할 수 있습니다. 그동안 쌓아 온 평판이 있으니 옆 팀도 맡은 서비스에 책임을 집니다. 그래서 소스를 일일이 읽지 않고도 쓸 수 있습니다.

Simon이 지적했듯 Claude Code에는 지켜야 할 평판이 없습니다. 코드를 잘못 짜도 책임을 물을 수는 없습니다. 그래도 일이 번번이 잘 풀리면 다음에도 믿고 맡기게 됩니다.

정해 둔 절차를 몇 번 건너뛰고도 별일이 없으면 어느새 그 정도는 괜찮다고 여깁니다. Simon은 이런 흐름을 [정상화된 일탈](https://simonwillison.net/2025/Dec/10/normalization-of-deviance/)로 설명합니다. 챌린저호 폭발 사고의 배경에도 이런 판단이 있었습니다. PR을 읽지 않고 몇 번이나 머지했는데 별일이 없었다면, 다음번에도 굳이 읽어야 하나 싶어집니다.

## 얼마나 오래 직접 써 봤는지가 중요합니다

요즘은 30분 만에 GitHub 저장소에 커밋 100개를 쌓고 README까지 보기 좋게 정리할 수 있습니다. 저장소만 봐서는 방금 만든 프로젝트인지 실제로 써 보며 검증한 프로젝트인지 가려내기 어렵습니다. Simon은 누군가 2주 동안 매일 써 본 프로젝트라면 더 믿을 만하다고 봤습니다.

에이전트가 짠 함수를 리뷰 없이 머지하려면 적어도 며칠은 입력값을 바꿔 가며 직접 호출해 봐야 합니다. 오늘 단위 테스트를 통과했다고 해서 내일 들어올 값까지 제대로 처리하리라는 보장은 없습니다.

혼자 쓰는 도구라면 이렇게 확인하기가 쉽습니다. 사이드 프로젝트를 매일 쓰다 보면 미처 손보지 못한 곳이 하나씩 눈에 들어옵니다.

실서비스에서는 새 버전에 트래픽을 조금씩 보내며 실제로 어떻게 돌아가는지 볼 수 있습니다. 배포 범위를 넓혀 가는 동안에도 서비스 상태를 계속 살필 수 있어야 합니다. 가령 카나리 배포로 새 버전에 트래픽의 5%를 며칠간 보내면서 지켜보는 일도 이런 의미에서는 코드 리뷰입니다.

---

머지 버튼을 누르기 전에 스스로에게 물어야 합니다. _나는 이 코드를 며칠이나 직접 써 봤나?_ 한 번도 안 써 보고 머지한다면, 에이전트가 준 코드를 그대로 받아 쓰는 바이브 코딩입니다.
