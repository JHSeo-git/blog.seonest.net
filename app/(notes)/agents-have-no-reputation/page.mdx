# 에이전트에게는 잃을 평판이 없다

<PostMeta createdAt={metadata.openGraph.publishedTime} />

Simon Willison은 [최근 글](https://simonwillison.net/2026/May/6/vibe-coding-and-agentic-engineering/)에 이렇게 썼습니다. "나는 이제 에이전트가 짠 프로덕션 코드를 한 줄씩 보지 않는다." 요즘 개발팀에서 드문 일은 아니지만, 그동안 Simon이 해 온 말을 생각하면 눈길이 가는 대목입니다.

## 흐려진 경계

Simon은 개인용 도구를 만들 때와 프로덕션 코드를 짤 때를 구분해 왔습니다. 혼자 쓸 도구는 코드까지 들여다보지 않고 결과만 받아 써도 괜찮다고 봤습니다. Simon이 말하는 _vibe coding_ 입니다. 프로덕션 코드라면 이야기가 다릅니다. AI의 도움을 받더라도 25년간 쌓은 개발 경험을 바탕으로 직접 판단하고 결과를 책임지는 방식을 그는 _agentic engineering_ 이라고 불렀습니다.

그런데 에이전트가 맡은 일을 잘 처리하다 보니 Simon도 어느 순간부터 코드를 한 줄씩 들여다보지 않게 됐습니다. Claude Code는 JSON API 엔드포인트에 SQL 쿼리를 연결하고 결과를 직렬화하는 작업을 실수 없이 끝내고, 테스트와 문서도 함께 작성합니다.

Simon은 다른 팀에서 운영하는 이미지 리사이즈 서비스를 예로 들었습니다. 이미지 크기를 바꾸려고 그 팀의 Git 저장소를 열어 소스부터 읽는 사람은 드뭅니다. 대개는 문서를 보고 필요한 함수를 호출합니다. 결과가 이상할 때라야 내부 구현을 들여다봅니다. 자기도 에이전트가 짠 코드를 그렇게 쓰기 시작했다는 얘기입니다.

## 그런데 에이전트에게는 잃을 것이 없습니다

옆 팀이 지난 분기에 서비스를 안정적으로 운영했고 다음 분기에도 계속 맡는다면, 문제가 생겼을 때 누구에게 고쳐 달라고 할지 압니다. 그 팀도 그동안 쌓은 평판이 있으니 자기 서비스에 책임을 집니다. 그걸 알기에 소스를 일일이 읽지 않고도 서비스를 쓸 수 있습니다.

Simon이 지적했듯 Claude Code에는 잃을 평판이 없습니다. 문제가 생겼을 때 책임을 물을 수도 없습니다. 그래도 맡길 때마다 잘 되면 쓰는 사람은 다음에도 잘하겠거니 하고 믿게 됩니다.

Simon은 이런 현상을 ["정상화된 일탈"](https://simonwillison.net/2025/Dec/10/normalization-of-deviance/)이라고 부릅니다. 정해 둔 절차를 몇 번 건너뛰어도 별일이 없으면 어느새 그 정도는 괜찮다고 여기게 됩니다. 챌린저호 폭발 사고가 그런 사례였습니다. PR도 읽지 않고 몇 번이나 머지했는데 문제가 없었다면 다음 PR만큼은 꼭 읽어야겠다고 생각하기가 갈수록 어려워집니다.

## 얼마나 오래 직접 써 봤는지가 중요합니다

Simon에 따르면 이제는 30분이면 커밋 100개에 README까지 잘 갖춘 GitHub 저장소를 만들 수 있습니다. 저장소만 봐서는 방금 만든 프로젝트인지, 오래 써도 괜찮을 만큼 검증한 프로젝트인지 구분하기 어렵습니다. 그가 믿을 만하다고 꼽은 단서는 누군가 그 프로젝트를 2주 동안 매일 써 봤다는 사실이었습니다.

에이전트가 짠 함수를 리뷰 없이 머지할 때도 믿을 근거는 있어야 합니다. 적어도 며칠은 여러 입력으로 직접 호출해 봐야 합니다. 오늘 단위 테스트를 통과했다는 사실만으로 내일 들어올 입력도 잘 처리하리라고 믿기는 어렵습니다.

개인용 도구라면 이렇게 확인하기가 쉽습니다. 사이드 프로젝트를 매일 직접 쓰다 보면 미처 다듬지 못한 부분을 모두 발견하게 됩니다.

실서비스에서는 새 버전에 트래픽을 조금씩 보내 실제로 어떻게 동작하는지 살필 수 있습니다. 배포 범위를 넓혀 가는 동안에는 서비스 상태도 계속 확인할 수 있어야 합니다. 카나리 배포로 트래픽의 5%를 며칠간 처리하며 지켜보는 일도 이런 의미에서는 코드 리뷰입니다.

머지 버튼을 누르기 전에 _이 코드를 직접 며칠이나 써 봤는가?_ 하고 물어야 합니다. 한 번도 써 보지 않았다면 다시 vibe coding을 하고 있는 것입니다.
